# STM32 / Peripheral Concepts Log

Running reference for STM32-specific and general peripheral concepts, built up as we go through the GPIO project and beyond. Companion to `c_rules.md` (core C) and `comp_arch.md` (architecture/memory/toolchain).

## Peripherals

A microcontroller chip is not just the CPU core. Bolted onto the same piece of silicon are many separate hardware sub-systems, each with its own job: one controls physical pins, one handles serial communication, one measures time, one does analog-to-digital conversion, etc. Each of these sub-systems is called a **peripheral** — real, distinct circuitry, separate from the CPU core, controlled entirely by writing to its own dedicated memory-mapped registers.

## GPIO

**G**eneral **P**urpose **I**nput/**O**utput — the peripheral whose job is: let software set a physical pin's output voltage (high/low), or read what voltage is currently on a pin from the outside world.

STM32 chips have several GPIO peripherals, one per "port," labeled with letters: `GPIOA`, `GPIOB`, `GPIOC`, etc. Each port controls a group of up to 16 physical pins (numbered 0–15). **PA5** = "Port A, pin 5" — on the Nucleo-F401RE, this specific pin is wired to LD2 (the onboard LED).

## Pin

Physically: the silicon die inside the chip package is far too small and fragile to wire to directly. The package (the black plastic/ceramic body you can actually see and solder) has metal legs sticking out — these are the **pins**. Each pin is connected internally to specific circuitry on the die via a tiny bond wire.

Externally, a pin is just a physical electrical contact point: something can apply voltage to it (input), something can drive voltage out of it (output), or it can carry power/ground/clock signals. Some pins are fixed-purpose (VDD/power, GND/ground, NRST/reset). Most are GPIO pins whose *role* is configurable in software — the same physical pin can act as a plain digital output, a digital input, or hand off to a different peripheral entirely (UART TX, SPI clock, etc.) depending on how its MODER (and later, alternate-function registers) are set.

On the Nucleo board, each chip pin is also broken out to a labeled header socket on the board's edge, so you can physically connect a jumper wire to it.

## RCC (Reset and Clock Control)

A peripheral itself, whose job is administrative: it controls the clock signal fed into every *other* peripheral, and handles reset logic. Every peripheral needs a clock signal to operate; RCC lets software turn each peripheral's clock on or off independently (saves power when a peripheral is unused — "clock gating").

## Bus grouping (AHB1, APB, etc.)

Peripherals are wired onto different internal communication buses inside the chip (separate internal "highways" connecting the CPU to clusters of peripherals). `AHB1` is the name of the bus GPIO ports happen to be on for this chip family — a label used by the reference manual to organize which enable bit lives in which register, not something to derive from first principles.

## Register naming pattern

- **ENR** = **En**able **R**egister — a register whose individual bits turn peripheral clocks on/off. `RCC_AHB1ENR` = "RCC's enable register for peripherals on the AHB1 bus." Bit 0 = GPIOA's clock enable, bit 1 = GPIOB, etc. (fixed by the chip design, looked up in the reference manual, not derived).
- **MODER** = **Mode** **R**egister — belongs to the GPIO peripheral itself (not RCC). Sets each pin's fundamental behavior: input / output / alternate-function / analog. 2 bits per pin.
- **ODR** = **O**utput **D**ata **R**egister — also belongs to GPIO. Holds the live output state (high/low) for each pin currently in output mode. Writing a bit here directly drives the physical pin voltage.

So the three `test.c` lines read as: turn on GPIOA's clock (RCC) → set PA5 to output mode (MODER) → toggle PA5's voltage (ODR).

## MODER bit-per-pin formula

Each pin gets a 2-bit mode field: pin `n` uses bits `2n` (LSB) and `2n+1` (MSB) of `MODER`. Encoding: `00`=input, `01`=output, `10`=alternate function, `11`=analog. PA5 → bits 10:11. PA6 → bits 12:13. Same formula for any port/pin.

## Don't rely on register reset values

Every register has a documented reset value (see the reference manual's register description tables) — but it is **not** uniformly zero everywhere. Example: PA13/PA14 on the F401 reset to alternate-function mode (not input), because those pins are wired to the SWD debug interface and ST wants debugging to work without extra config.

Even where a reset value *is* zero, don't write code that depends on it. Power-on reset isn't the only path into `main()` — watchdog resets, software resets, and bootloader jumps don't always restore every peripheral to its power-on state. Professional practice: explicitly drive every register field you care about to the exact value you want (set the bits that must be 1, clear the bits that must be 0), regardless of assumed prior state. This is also why `GPIOA_MODER |= (1<<10); GPIOA_MODER &= ~(1<<11);` is written as two explicit operations rather than relying on the field already being right.

## Vector table

An array of addresses, placed at the very start of FLASH (pinned there via `__attribute__((section(".isr_vector")))` + `KEEP()` in the linker script — see `build_systems.md`). Entry 0 is special: it's a raw address *value* (top of RAM) that the CPU hardware itself loads directly into the stack pointer at power-on, before executing any instruction — no software runs to make this happen, it's wired into the Cortex-M reset behavior. Entry 1 is `Reset_Handler`'s address — the first real code executed, jumped to using that same hardwired reset mechanism.

Our build only implements slots 0 and 1. A real STM32F401 vector table has ~90+ slots after that — one per exception/interrupt type (NMI, HardFault, SVCall, PendSV, SysTick, then every peripheral interrupt: timers, USARTs, DMA channels, EXTI lines, etc. — full list in the reference manual's vector table chapter). Each slot is a "vector" — a pointer to a handler function. When an interrupt fires, the CPU looks up that interrupt's slot number in this same table and jumps to whatever address is stored there — identical mechanism to the reset entry, just triggered by a different event. This table is the hardware foundation the whole Interrupts topic is built on.

Forward reference: **VTOR** (Vector Table Offset Register) lets the table be relocated elsewhere in memory at runtime — relevant once a bootloader needs to hand off to a separately-flashed application.

## Timer milestone: polling-based delay on TIM2 (verified working)

Replaced the busy-wait `for(volatile int i...)` delay with a real hardware timer, polling-driven (no interrupts yet). Registers used, all on TIM2 (APB1 bus, base `0x40000000`):

- `RCC_APB1ENR` (bit 0 = `TIM2EN`) — **correct address is `0x40023840`** (offset `0x40` from RCC base `0x40023800`), *not* `0x1C` as first looked up. Confirmed by cross-checking the CMSIS RCC struct layout: `AHB1ENR`(0x30) → `AHB2ENR`(0x34) → `AHB3ENR`(0x38) → reserved(0x3C) → `APB1ENR`(0x40).
- `TIM2_CR1` (offset `0x00`) — bit 0 = `CEN` (counter enable), set *last*, after `PSC`/`ARR` are configured (enabling first would start counting with stale reset-value `PSC`/`ARR`).
- `TIM2_PSC` (offset `0x28`), `TIM2_ARR` (offset `0x2C`), `TIM2_CNT` (offset `0x24`) — plain value registers, assigned directly with `=` (not `|=`), since each holds one whole number, unlike `MODER`'s packed multi-pin bit fields.
- `TIM2_SR` (offset `0x10`) — bit 0 = `UIF` (update flag). Status bit, not a control bit: hardware sets it, software must explicitly clear it (`&= ~(1<<0)`) after acting on it, or the poll loop breaks after the first cycle.

**Timing formula**: `overflow_period_s = ((PSC+1) * (ARR+1)) / TIMxCLK`. Chose `PSC=15999` to divide the default 16 MHz HSI-derived `TIM2CLK` down to a clean 1 kHz (1 ms/tick), then `ARR` = desired milliseconds − 1 (e.g. `ARR=499` → 500 ms, `ARR=1999` → 2 s).

**Debugging story worth remembering**: LED stayed off with correct-looking code. Isolated the fault with the "LED as oscilloscope" technique — first proved GPIO/build/flash still worked (unconditional `ODR` write lit the LED), then proved `TIM2_CNT` was stuck at 0, then proved `TIM2_CR1`'s `CEN` bit wasn't sticking. That narrowed it to "TIM2 never actually got clocked," which traced back to the wrong `RCC_APB1ENR` address above. Lesson: when hardware doesn't behave and the code logic checks out, re-verify the *chip-investigation facts* themselves against a primary source rather than assuming the bug is in your reasoning.

Verified on hardware with both `ARR=499` (0.5s) and `ARR=1999` (2s) — blink rate changed correspondingly, confirming genuine timer-driven behavior.

## Timer milestone 2: interrupt-driven TIM2 (verified working)

Converted the polling loop to a real interrupt. New pieces, on top of everything above:

- **`TIM2_DIER`** (offset `0x0C`), bit `UIE` — tells TIM2 to actually *request* an interrupt when `UIF` sets (previously `UIF` just sat there passively for polling to notice).
- **NVIC** (`NVIC_ISER0`, address `0xE000E100`, bit = IRQ number) — a separate ARM-core peripheral (documented in ARM's own Cortex-M4 TRM, not ST's RM0368, since it's identical across every Cortex-M4 vendor) that must independently let a specific interrupt line through. Same two-layer-permission shape as RCC clock gating: peripheral requests, NVIC gates it through.
- **Vector table expansion**: TIM2's IRQ number is 28; its vector table slot is index `16 + 28 = 44` (the first 16 slots are the fixed ARM core exceptions). Expanded `vector_table` from 2 entries to 45, using GCC's designated-initializer range extension `[2 ... 43] = Default_Handler` to fill all unused slots with a safe trap function instead of leaving them pointing at raw garbage bytes.
- **`Default_Handler`**: a shared `while(1){}` trap for any unimplemented exception/interrupt — predictable, debuggable landing spot instead of the CPU jumping into undefined memory.

**Bugs caught during this pass, worth remembering:**
1. Forward-declaring a function *after* its first use (`Default_Handler` used in the array before being declared) — straightforward compile error, fixed by declaring it earlier.
2. **Macros vs. extern'd variables** — tried `extern volatile uint32_t GPIOA_ODR;` in `startup.c` to "share" a register defined as a `#define` in `test.c`. This compiles but is wrong: `GPIOA_ODR` is a macro (preprocessor text substitution, no linkage), not a real variable, so `extern` silently creates a brand-new, meaningless RAM variable with that name instead of referring to the hardware register. Fix: moved the register macros into a shared `registers.h`, `#include`d by both files — `extern` is for sharing real variables/functions across translation units; `#include` is for sharing macros/declarations. Consequence if left unfixed: the ISR would never actually clear the real `UIF`, causing the interrupt to keep re-firing back-to-back forever.
3. **`#include <registers.h>` vs `#include "registers.h"`** — angle brackets are conventionally for toolchain/system headers and aren't guaranteed to search the project directory; quotes are guaranteed to check the source file's own directory first. Own project headers should use quotes.

Verified on hardware: LED now blinks every 2 seconds with zero polling in `main()` — `main()` just configures everything once and sits in an empty `while(1);`; the actual toggle happens entirely inside `TIM2_IRQHandler`, invoked automatically by hardware.

## USART milestone: polling-based TX + RX echo on USART2 (verified working)

Register-level, no HAL. USART2 is on the APB1 bus, base `0x40004400`.

**Pin routing — GPIO alternate function, not GPIO output.** UART TX/RX pins aren't driven by software toggling `ODR`; the USART peripheral itself drives the pin electrically, software just has to hand the pin over to it:
- `MODER` = `10` (alternate function) for PA2 (TX) and PA3 (RX) — same 2-bit-per-pin field as GPIO output mode, just a different encoded value.
- `AFRL` (4 bits per pin, pins 0–7) = `0111` (AF7) on both PA2 and PA3 — AF7 is the specific "alternate function slot" wired to USART2 on this chip (looked up in the datasheet's alternate function table, not derivable from first principles, same as the AHB1/APB1 bus assignment).

**Core registers:**
- `USART2_CR1` — `UE` (bit 13, master enable), `TE` (bit 3, transmitter enable), `RE` (bit 2, receiver enable). All three must be set or nothing works.
- `USART2_BRR` — 12-bit mantissa + 4-bit fraction packed into one register: `(mantissa << 4) | fraction`. For 115200 baud at a 16 MHz `PCLK1`: `USARTDIV = fCK / (16 × baud) ≈ 8.68` → mantissa `8`, fraction `11` (0.68 × 16 ≈ 11). Assigned with plain `=`, not mask-and-shift, since the whole register is one self-contained value with no other fields to preserve.
- `USART2_SR` — status register. `TXE` (bit 7, transmit data register empty — set when it's safe to write the *next* byte) and `RXNE` (bit 5, receive data register not empty — set when a received byte is waiting to be read).
- `USART2_DR` — a single address, hardware-aliased: writing it loads the transmit shift register (TDR), reading it drains the receive buffer (RDR). Same address, two different physical registers underneath depending on read vs write direction.

**TXE/RXNE clearing semantics — not uniform, unlike `UIF`:** `TXE` clears itself automatically the instant `DR` is written; `RXNE` clears itself automatically the instant `DR` is read. Neither needs an explicit `&= ~(1<<n)` the way `TIM2_SR`'s `UIF` does — a different flag-clearing convention per peripheral, always worth checking the reference manual rather than assuming.

**Send pattern:** for each byte, `while (!TXE) {}` then `DR = byte`. The wait is mandatory *before every single byte* — writing back-to-back without waiting clobbers whatever was still being shifted out, since `DR` is a single-slot buffer, not a FIFO.

**Bugs and lessons from this pass, worth remembering:**
1. **Wrong clock bus** — `RCC_AHB1ENR` used instead of `RCC_APB1ENR` to enable USART2's clock. USART2 lives on APB1 (bit 17), not AHB1 (that's GPIO's bus). Same "look it up, don't assume" lesson as the RCC address bug in the timer milestone.
2. **Operator precedence**: `(USART2_SR >> 7) & 1 == 0` parses as `(USART2_SR >> 7) & (1 == 0)` because `==` binds *tighter* than `&` in C — a genuinely easy-to-miss precedence trap. Always wrap the full bitwise expression in its own parens before comparing: `((USART2_SR >> 7) & 1) == 0`.
3. **Multi-character constant**: `USART2_DR = '\r\n';` compiles, but `'\r\n'` is a single `int` with an implementation-defined packed value — not "two bytes, `\r` then `\n`." It's one register write, and the hardware shift register only sees the low bits, so at best one of the two characters actually reaches the wire. GCC warns about this with `-Wmultichar` under `-Wall` — a good example of why to always build with warnings on. Fix: two independent writes, each with its own `TXE` wait, exactly like every other byte in the loop.
4. **Bare `\n` vs `\r\n`** — a terminal/protocol convention issue, not a register bug. `\n` (LF) moves the cursor down a row but not back to column 0; `\r` (CR) does the reverse. A real "new line" on a raw serial link is the two-byte sequence `\r\n`. On Linux, the OS tty driver silently expands `\n` → `\r\n` for you in cooked mode, which is why this is easy to forget — bare-metal UART has no such translation layer, so the firmware itself has to send both bytes.
5. **PuTTY local echo doubling** — with `Terminal → Local echo` on "Auto," PuTTY echoed the typed keystroke locally *in addition to* the firmware's own `"GOT: <char>"` remote echo, interleaving both on screen and looking like corrupted/duplicated output. Since the device already echoes every byte back, local echo must be forced off (`Terminal → Local echo → Force off`).
6. **Tooling isn't always the firmware's fault** — VS Code's Serial Monitor extension silently failed to render incoming bytes at all (known upstream bug); switching to PuTTY was correct, but PuTTY then failed too, for an unrelated reason: a wedged Windows COM-port driver state that only cleared after a full reboot, not fixable from any application setting. **Diagnostic order that isolated this**: proved TX completion via LED-as-oscilloscope (no PC involved at all) before ever trusting what any terminal displayed — the same discipline as the timer bug's "recheck the facts, not just the code" lesson. When a symptom persists across two independent, correctly-configured applications, suspect the OS/driver layer underneath both, not either application.

Verified on hardware end-to-end: typing a character in PuTTY produces a clean `GOT: <char>` on its own line, byte-by-byte transmission confirmed both by design (explicit per-byte `TXE` wait) and by the fact that render latency (~1 ms for the whole reply) is far below anything perceptible.

7. **USB composite device enumeration race at boot** — same "silent PuTTY" symptom recurred later, again with firmware proven correct via LED diagnostics. This time the fix was unplugging and replugging the board, not a reboot. Root cause: the ST-Link is a USB *composite* device (debug interface + virtual COM port bundled as separate USB interfaces on one physical connection). If the board is already powered and plugged in before Windows finishes booting, enumeration can happen before the CDC/serial driver stack is fully loaded — the debug interface binds fine, but the VCP interface is left half-initialized: it shows up in Device Manager with a normal-looking COM number, but nothing actually flows through it. Unplug/replug forces a full re-enumeration once drivers are already loaded, fixing it. Cheaper first move than a reboot for this symptom; plug the board in after boot when possible to avoid it entirely.

## USART milestone 2: interrupt-driven RX (verified working)

Converted RX from polling (`while(1) { if (RXNE) ... }` in `main()`) to interrupt-driven, same shape as the TIM2 interrupt milestone: peripheral-level arm → NVIC-level arm → vector table slot → ISR does minimal work, `main()` does the rest.

**New pieces:**
- **`USART2_CR1` bit 5 (`RXNEIE`)** — arms the peripheral to actually *request* an interrupt when `RXNE` sets, same two-layer relationship as `TIM2_DIER`'s `UIE`: the status flag exists either way, but nothing reaches the NVIC until this bit says so.
- **`NVIC_ISER1`, not `ISER0`** — `TIM2`'s IRQ (28) fit in `ISER0`, which only covers IRQ 0–31. USART2's IRQ is 38, out of that register's range entirely. The NVIC exposes multiple `ISERn` registers, each covering the next 32 IRQ numbers at a fixed `+4` byte spacing (`ISER0` = `0xE000E100`, `ISER1` = `0xE000E104`). IRQ 38 → `ISER1`, bit `38 − 32 = 6`.
- **Vector table slot `54`** (`16 + 38`, same formula as TIM2's slot 44) — array grown from 45 to 55 entries, new gap slots (45–53) filled with `Default_Handler`, slot 54 pointing at `USART2_IRQHandler`.
- **Data-carrying flag pair**: `tick_flag` (timer milestone) only ever needed to say "something happened." RX needs to hand over *which byte* arrived, so it's `volatile int rx_ready_flag` + `volatile char received_char` together — the flag says "there's a value ready," the variable holds the value. ISR writes both (char first, flag last); `main()` reads the char only after observing the flag, then clears the flag itself once fully done consuming it.
- **`usart2_write_byte()` extracted into `usart2.c`/`usart2.h`** — collapses the repeated `while(!TXE){} / DR = x` pattern into one function, called once per byte from `main()`. Mirrors the existing `registers.h` split: register *addresses* stay in the shared header, *behavior* lives in its own small driver file.

**Bugs caught during this pass:**
1. **Forgot to add the new source file to the build/link step** — `usart2.c` compiled fine on its own (the compiler only needs the declaration in `usart2.h` to generate call instructions), but linking failed with `undefined reference to 'usart2_write_byte'` plus a confusing `dangerous relocation: unsupported relocation` / `Unknown destination type (ARM/Thumb)` message. That second error is just the linker's fallback description for "I have a branch instruction here and no idea what's at the other end, because there *is* no other end" — the real signal is the plain "undefined reference" line above it. Fix: add every new `.c` file to the compile+link command, not just `#include` its header.
2. **Flag cleared unconditionally, outside the `if`** — `rx_ready_flag = 0;` was briefly placed *after* the `if (rx_ready_flag)` block instead of inside it, executing on every loop pass regardless of whether anything was actually consumed. This reopens a race: if a new byte arrives (setting the flag again) in the gap between the `if` block finishing and that unconditional clear line running, the new event gets silently wiped before `main()` ever acts on it. Fix: clear the flag as the last thing inside the same `if` block that consumed it, so "consumed" and "cleared" stay atomic with respect to each other from `main()`'s point of view.
3. **Missing include guards** — `registers.h` and `usart2.h` had no `#ifndef`/`#define`/`#endif` wrapper. Since `test.c` includes both `registers.h` directly *and* `usart2.h` (which itself includes `registers.h`), the header's contents were being pasted into the translation unit twice. This happened to compile cleanly only because every line is a `#define` with an identical replacement list each time, which C permits — the moment the header gains a `typedef`, struct, or `static inline` function, the same double-inclusion becomes a hard redefinition error. Fixed with standard `#ifndef HEADER_H / #define HEADER_H / ... / #endif` guards in both headers.
4. **Single-variable RX hand-off has no buffering** — noted, not fixed (fine for this use case): if a second byte arrives while `main()` is still mid-send on the first one, `received_char` gets silently overwritten by the ISR before the old value was ever used. A real multi-byte-per-burst use case would need a ring buffer instead of one shared variable.

**Debugging story worth remembering**: after the interrupt wiring compiled and linked, PuTTY went silent again. Rather than guess, re-ran the same LED-as-oscilloscope discipline from the timer bug and the first USART milestone, in order: (1) forced the LED on unconditionally as the very first line of `USART2_IRQHandler` — confirmed the ISR was genuinely being entered, ruling out `RXNEIE`/`ISER1`/vector-table wiring; (2) confirmed `TIM2_IRQHandler` kept blinking the LED afterward — proved `main()` wasn't hung or crashed, execution was genuinely returning from the ISR; (3) reused the `got_rx`/`sent_ok` flag pair to prove `main()` both saw the flag and that all three `usart2_write_byte()` calls returned normally (no `TXE` hang). All three checks passed — meaning the firmware was provably correct at every single stage — and the actual fault was external the whole time (see bug #7 above). Lesson repeated a third time this project: when hardware-level proof says the code is right, stop reading the code and start suspecting the layer underneath it.

## Interrupts as a general topic: priority, nesting, latency, critical sections

Covered as its own cross-cutting detour once two independent interrupt sources (`TIM2`, `USART2`) existed side by side to reason about concretely, rather than staying purely hypothetical.

- **Priority numbering is inverted**: a *lower* numeric value means *higher* actual urgency (priority 0 is most important). STM32F4 implements 4 priority bits per interrupt (16 levels), stored in `NVIC_IPRx` registers, one byte per IRQ, upper nibble used.
- **Equal priority never nests.** If one ISR is already executing, an equal-priority interrupt just waits its turn — no preemption. If two interrupts become pending at the exact same instant with equal priority (never actually resolved by "which is faster"), the NVIC's tie-break is fixed in hardware: lower IRQ number wins, deterministically, unrelated to either handler's code.
- **Nesting mechanics**: Cortex-M automatically "stacks" (pushes) 8 registers (`R0-R3`, `R12`, `LR`, `PC`, `xPSR`) on exception entry, and unstacks them on return — pure hardware, not compiler-generated, which is why ISRs can be plain C functions with no manual register-save assembly (unlike classic AVR/8051). A higher-priority interrupt preempting a lower one triggers a second stacking on top of the first; unwinds cleanly, LIFO, same principle as nested function calls but hardware-driven instead of compiler-generated.
- **ISR latency** = time from the hardware event to the ISR's first instruction. Three components: fixed hardware entry overhead (~12 cycles on Cortex-M4, undoable), priority-based blocking (this project's "keep ISRs short, defer real work to `main()` via a flag" discipline directly minimizes this), and critical sections (below). Concrete stake for this project: at 115200 baud, one UART byte is ~87µs — exceed that as a worst-case latency budget and `USART2_DR`'s single-slot buffer overruns (`ORE`), silently losing data.
- **Critical sections**: deliberately masking interrupts (`CPSID I`/`CPSIE I`, via `PRIMASK`) to protect a shared multi-step operation from being torn by an ISR mid-sequence — same concept as a mutex, just arbitrating between main-line code and a hardware interrupt instead of OS threads. Implemented as `disable_irq()`/`enable_irq()`, `static inline` in their own `irq.h` (not tied to any one peripheral, since every future driver needs them) — `static` avoids C's tricky plain-`inline` external-linkage rules, `inline` matters because the whole point is to keep the protected window as few instructions as possible, and a real function call's overhead would itself eat into that window. **Applied correctly** to the `received_char` RX race: snapshot into a local variable inside the lock, release the lock immediately, do the slow part (`usart2_write_byte` calls) *outside* it — never hold a critical section across a blocking operation, that just maximizes the latency hit on everything else.
- **Common mistake caught in this project's own code**: wrapping a slow, blocking SPI loopback transfer in `disable_irq()`/`enable_irq()` despite there being no shared-variable hazard to protect at all — a misapplication of the pattern that would have frozen out `TIM2` and `USART2` for the full duration of the transfer. Caught before it shipped.

## SPI milestone: master-mode loopback on SPI1 (verified working)

Same three-stage pattern as every peripheral: clock enable, GPIO alternate-function config, peripheral control register — plus one new wrinkle SPI introduces that UART/TIM2 didn't have (multi-signal full-duplex framing).

- **Peripheral**: `SPI1`, base `0x40013000`, on **APB2** (first peripheral this project put there — `RCC_APB2ENR` bit 12 = `SPI1EN`, address `0x40023844`, found by extending the same fixed-offset pattern already used for `AHB1ENR`/`APB1ENR`).
- **Pins**: `PA5`=`SCK`, `PA6`=`MISO`, `PA7`=`MOSI`, all alternate function `AF5` — found in the *datasheet's* AF table, not the reference manual, same distinction as USART2's `AF7`. Real gotcha: `PA5` is the exact same physical pin as `LD2`, the onboard LED used for every diagnostic all project — configuring SPI1 on default pins means losing the LED as a GPIO output for the duration. (Fix exists via desoldering solder bridge `SB21` and rerouting to a spare pin, or simpler: breadboard an external LED on a free pin instead — deferred, not yet done.)
- **`SPI1_CR1` bits**: `CPHA`=bit0, `CPOL`=bit1 (order easy to get backwards — both `0` selects Mode 0), `MSTR`=bit2, `BR[2:0]`=bits3-5 (baud prescaler, chosen conservatively at `/64` → 250kHz for reliable breadboard-jumper signal integrity on a first bring-up, not max speed), `SSM`/`SSI`=bits9/8, `SPE`=bit6. **Sequencing rule**: `SPE` must be set *last*, only after `CPOL`/`CPHA`/`MSTR`/`BR` are already correct — RM0368 documents changing clock config while `SPE=1` as undefined behavior.
- **`SPI1_SR`/`SPI1_DR`**: base+`0x08`/base+`0x0C`. Bit layout is its own shape, not reusable from USART2 by habit: `RXNE`=bit0, `TXE`=bit1 here (USART2 had them at 5/7). Both flags are pure hardware-driven and self-clearing (`TXE` clears on `DR` write, `RXNE` clears on `DR` read) — never need manual clearing, unlike `TIM2_SR`'s `UIF`.
- **`SSM`/`SSI` (bits 9/8)**: needed because this project drives chip-select manually via a plain GPIO pin rather than the dedicated hardware `NSS` pin. Without them, the peripheral watches its own (unconnected/floating) `NSS` pin even in master mode, as a **multi-master bus-conflict safety feature** — if `NSS` ever reads low, hardware assumes a bus contention risk (two masters potentially driving `SCLK`/`MOSI` simultaneously) and trips a protective fault (`MODF`), automatically clearing `MSTR`. `SSM=1` disconnects that watching entirely; `SSI=1` forces the internal substitute value to "high" (not selected) — getting `SSI` backwards (`0`) would immediately self-trigger the exact fault being avoided, so both bits have to be right together, not just `SSM` alone.
- **Full-duplex shift-register model**: `MOSI`/`MISO` are two ends of one continuous shift-register loop spanning master and slave; every `SCLK` edge shifts a bit out one side and in the other, simultaneously, on both wires — which is why one transfer function (`spi1_transfer_byte`) both writes and reads, unlike UART's separate TX/RX paths.
- **`CS` is entirely software's responsibility once `SSM=1`** — no hardware automation at all. A real slave device needs a plain GPIO pin manually pulled low before the transfer and high after; skipped for this first loopback test since there's no real slave chip involved yet, only the MCU talking to itself over a `MOSI`→`MISO` jumper wire.
- **File organization**: `usart2.c`/`usart2.h` renamed to `serial_interfaces.c`/`serial_interfaces.h` and consolidated, anticipating I2C landing in the same file later — a deliberate "grouped by category (serial comms), disambiguated by function name (`usart2_`/`spi1_`/future `i2c1_` prefixes)" choice, a step beyond the project's earlier one-file-per-peripheral pattern (`gpio.c`, `irq.h`).
- **`configure_gpio()` extracted to its own `gpio.c`/`gpio.h`** as pin count grew past comfortable inline repetition in `main()` — caught and fixed two real bugs during that move: `PA6` had `AFRL` set but no matching `MODER` alternate-function bit (silently inert without it), and `PA7`'s config accidentally targeted `MODER` with an `AFRL`-shaped mask/value, which would have also corrupted **`PA14` (`SWCLK`, one of the two SWD debug pins)** — a real risk of severing debugger access to the board, not just a "this one pin doesn't work" bug.

**Verified on hardware**: `MOSI` jumpered directly to `MISO` (no external slave device), sending `'A'` through `spi1_transfer_byte()` once per `TIM2` tick and echoing the returned byte over `usart2_write_byte()` — `'A'` confirmed coming back cleanly in PuTTY, proving the full chain (clock config, GPIO routing, master-mode framing, full-duplex shift) end to end before ever bringing a second physical device into the picture.

## First breadboard exercise: external LED on PA8 (verified working)

Closed out the `PA5`/`LD2` conflict from the SPI milestone by moving the blink target to `PA8` (confirmed free — not used by USART2, SPI1, or the SWD pins), driven through a real external LED on a breadboard for the first time.

- **Breadboard topology**: within one half, holes sharing the same row *number* (e.g. `f10`...`j10`) are one electrically connected terminal strip; different row numbers are isolated from each other, and the two halves (`a`-`e` vs `f`-`j`) are isolated by the center gap. A two-leg component's legs must land in two different nodes — either different row numbers in the same column letter (simplest, no gap-bridging), or the same row number straddling the gap.
- **LED polarity**: long leg = anode (toward the current-limiting resistor/GPIO side), short leg = cathode (toward GND); flat edge on the LED body is a second way to identify the cathode side if legs get trimmed.
- **Current-limiting resistor is mandatory, and value matters a lot**: `I ≈ (Vgpio − Vled_forward) / R`. First attempt used a 100kΩ resistor by mistake → ~13µA, barely visible (LEDs want roughly 5–20mA to look properly lit — off by ~1000x). STM32 GPIO pins have an absolute max current rating around 20mA; a 10Ω resistor was correctly rejected before use (~130mA, >6x over the limit — real risk of damaging the pin and/or LED). Settled on 220Ω (~5.9mA) as the safe option actually available in the kit; 100–150Ω would have been the ideal "clearly bright, comfortable safety margin" sweet spot if on hand.
- **Same `gpio.c`/`startup.c` bug pattern caught again**: `GPIOA_MODER |= (1 << 17)` instead of `(1 << 16)` for `PA8`'s 2-bit field — set the *wrong* bit of the pair, silently producing alternate-function mode instead of output (would have made the LED toggle a no-op with no error anywhere). Same root cause as the PA6/PA7 bugs from the SPI milestone: off-by-one-bit within a multi-bit field, still the single most recurring mistake class this project.

Verified on hardware: LED visibly, safely bright, blinking on the same `TIM2`-driven 1-second cadence the onboard `LD2` used to run before `PA5` was reassigned to `SPI1_SCK`.

## ADC milestone: single-channel polled read of a potentiometer on PA0 (verified working)

Same three-stage register pattern again — clock enable (`RCC_APB2ENR` bit 8, `ADC1EN`), GPIO analog config (`PA0` `MODER` = `11`), peripheral setup (`ADC1_CR1`/`CR2`/`SQR1`/`SQR3`) — plus resolution/alignment/sequencing concepts specific to ADC.

- **Resolution vs. precision trade-off**: `CR1` `RES` bits set to `10` (8-bit, 256 levels) instead of the chip's native 12-bit (4096 levels) — fewer bits means a shorter conversion and simpler downstream handling, at the cost of quantization precision. Fine for watching a knob move; would need the full 12 bits (or oversampling) for something like a precision sensor.
- **`ALIGN`**: right-aligned chosen — result sits in `DR`'s low bits, no shifting needed to read it directly.
- **`SQR1`/`SQR3`**: sequence-length and channel-select registers — only one channel (`ADC1_IN0`) in use here, but this is the same path a multi-channel scan would extend through.
- **Retrieval method**: single-conversion, start-bit-then-poll-`EOC`-then-read-`DR`. Simplest possible pattern, and the most CPU-blocking one — fine with nothing else competing for CPU time in this superloop, but the reason interrupt-driven EOC and DMA-driven ADC (next up) exist is that polling doesn't scale past "one channel, nothing else to do."
- **`VREF+`/`VDDA`**: the ADC's digital count is a *ratio* against `VREF+`, not an absolute voltage — a noisy or drifting reference shows up as reading jitter with zero relation to the actual input. On the F401RE's LQFP64 package, `VREF+` isn't broken out as its own pin at all — internally tied straight to `VDDA`, so reference stability here is exactly as good as the `VDDA` rail and nothing more (no external precision-reference option on this chip).
- **Manual decimal-to-ASCII conversion for UART output**: `usart2_write_byte` sends one raw byte, not human-readable text — a `uint16_t` reading needed its own digit-extraction pipeline (`usart2_write_uint16`/`get_int_len` in `serial_interfaces.c`) rather than routing through `usart2_write_byte` directly. Real bug caught mid-build: extracting digits via `% 10`/`/ 10` naturally yields them least-significant-first, so writing each digit to `message[digit_length - i]` (off by one, and backwards) left one buffer slot always uninitialized and dropped the correctly-computed last digit — fixed to `message[digit_length - 1 - i]`. Also caught: `2^16` used as an "is this over 16 bits" guard — `^` is bitwise XOR in C, not exponentiation, so the check silently evaluated to `number > 18`, not `number > 65536`.
- **Floating analog input reads noise, not zero**: confirmed directly — `PA0` configured analog but physically unconnected read garbage, not a clean `0`, because a floating high-impedance node has no defined voltage and picks up whatever's around it.
- **Connection quality is part of signal integrity, not just firmware**: an intermittent/loose wiper contact produced a fast, repeating full-scale sawtooth (~255 → ~0 → ~255 every 10-13 one-second samples) that looked nothing like a hand smoothly turning a knob — resolved by reseating the connection, not by touching any code.
- **Wrong-pin mixup on the Nucleo header**: chasing a "3.3V wire kills the breadboard LED" symptom that reproduced even after moving to fresh wires in a different breadboard location — most likely cause was grabbing a neighboring pin in the same power cluster (`RESET`/`IOREF`/`VBAT`/`5V` all sit tight next to `3V3` on both Nucleo power headers) rather than an actual breadboard fault; a momentary `RESET` assertion would explain the instant "recovery" on unplugging far better than a genuine short would.

Verified on hardware: potentiometer wired as a voltage divider (outer legs to `3V3`/`GND`, wiper to `PA0`) produces smooth, stable 0-255 readings across its full sweep, printed as correct multi-digit decimal text over USART2 once per `TIM2` tick.

## DMA milestone: continuous ADC1 sampling via DMA2, circular single-buffer + half/full-transfer interrupts (verified working)

Replaced the previous milestone's CPU-blocking `adc1_read()` poll (start conversion, wait `EOC`, read `DR`) with `ADC1` in continuous mode streaming samples into RAM entirely via `DMA2`, with zero CPU involvement per sample.

- **Fixed hardware routing vs. configurable behavior**: which stream+channel talks to which peripheral (`ADC1` = `DMA2` Stream 0 / Channel 0, per RM0368's request-mapping table) is a hardwired silicon fact, not a choice — same category as `AF5`/`AF7` pin mappings. Everything inside `DMA2_S0CR` once you're on the right stream (direction, sizes, increment modes, priority, interrupt enables) is fully software-configurable.
- **Design chosen over double-buffer mode**: circular mode (`CIRC`) with a single buffer, split into two logical halves via `HTIE`/`TCIE` (half-transfer + transfer-complete interrupts), instead of `DBM` double-buffer mode (`M0AR`/`M1AR` hardware pointer-swap). Same tearing-avoidance guarantee — each half is only read while DMA is guaranteed to be filling the *other* half — with fewer registers in play (`M1AR` never used, so never defined). `DMA2_HISR`/`DMA2_HIFCR` also intentionally never defined — those cover streams 4-7's flags, irrelevant to Stream 0.
- **`ADC1_CR2` needs `DMA` (bit 8) *and* `DDS` (bit 9), not just one.** `DMA` alone only lets the ADC request a transfer once; without `DDS=1`, requests stop being issued after that first transfer even though `CONT=1` keeps the ADC converting forever. Both bits together are what's needed for indefinite streaming.
- **`DMA2_S0PAR`/`M0AR`/`NDTR` are not optional extras** — without them explicitly set, a stream can have `EN=1` and every other bit perfect and still move nothing, since source/destination/count all reset to `0`.
- **DMA's flag-clear convention is the opposite of every status register touched so far.** `TIM2_SR`'s `UIF` and `USART2_SR`'s flags clear by writing 0 to the same register you read. `DMA2_LISR` (status, read-only) and `DMA2_LIFCR` (a separate, write-1-to-clear register) don't work that way — writing `1` to a bit in `LIFCR` clears the matching flag in `LISR`; writing `0` does nothing. Getting this backwards (`&= ~bit` instead of `|= bit`) means the flag never actually clears, so the interrupt re-enters itself the instant it returns — same root category (never-cleared flag, re-firing forever) as the very first `TIM2`/`UIF` bug from the original NVIC milestone, just a different specific mechanism. The write-1-to-clear shape exists specifically so clearing one flag can never race-clobber a different flag that hardware sets in the same register in the gap between a read and a write-back.
- **`extern`/definition qualifier mismatches are real compile errors, not warnings**: `registers.h` declared `extern volatile uint8_t dma_sample_buffer[20]`, but the actual definition in `startup.c` briefly had no `volatile` (and briefly no type at all — bare `volatile dma_sample_buffer[20];`, silently defaulting to `int` under pre-C99 implicit-int rules, which is a hard error under `-std=c17`). Both the qualifier and the base type of a declaration and its definition must match exactly.
- **Array decay misuse caught**: `DMA2_S0M0AR = &dma_sample_buffer;` compiles and even produces the numerically correct address, but it's the wrong construction — `&dma_sample_buffer` is "pointer to the whole 20-byte array" (`uint8_t(*)[20]`), not "pointer to its first byte." Plain `dma_sample_buffer` already decays to the latter in this context (assignment RHS is "most expression contexts," not just function-call arguments, which is where decay was first introduced). Correct form: `(uint32_t)dma_sample_buffer`.
- **`SWSTART` ordering race, the actual root cause of "one sample arrives, then total silence forever"**: `ADC1_CR2`'s `SWSTART` bit was written before `DMA`/`DDS` and before `DMA2` itself was even clocked or armed. Software executes fast enough relative to one ADC conversion that the *first* conversion could complete before the DMA side was ready to catch it, leaving the ADC's continuous-request handshake with `DMA2` never cleanly established. Fix: `SWSTART` written exactly once, as the literal last line of setup, after `DMA2_S0CR`'s `EN` bit — same "arm every downstream consumer before starting the producer" discipline as `TIM2`'s `CEN` and `SPI1`'s `SPE`.
- **Sanity-check surprising counters against expected order of magnitude before calling them a bug.** `half_sample` appearing to "never clear" at a few thousand per print was not a reset bug — `half_sample = 0` was firing correctly every tick, but the real underlying event rate (tens of thousands of `HTIF`/`TCIF` events per second, once DMA was genuinely running continuously) meant it reliably re-accumulated to a similar ballpark within the same ~1-second window every time. Confirmed by estimating expected conversions/second from the ADC's resolution/sampling-time/prescaler settings rather than assuming a large number must mean something's broken.
- **A single-byte read needs no `HTIF`/`TCIF` synchronization at all.** The half-buffer safety discipline exists to protect *coherent multi-sample batches* (e.g. averaging a whole half) from being torn by DMA overwriting part of it mid-read. Peeking at one `uint8_t` array slot for a quick print is atomic regardless of DMA activity — there's no partial/torn single-byte read possible on this bus.

Verified on hardware: potentiometer readings stream continuously into `dma_sample_buffer` via `DMA2` Stream 0 with zero per-sample CPU polling, tracking the knob's rotation live over USART2, with the half/full-transfer interrupt firing at a real, sanity-checked high rate confirming the whole circular-DMA pipeline is genuinely running rather than idle.

## I2C milestone: I2C1 master bus-scanner + I2C2 slave, self-loopback (verified working)

No external I2C device available yet, so proved the driver against itself: `I2C1` (master, `PB8`=`SCL`/`PB9`=`SDA`) bridged on a breadboard to `I2C2` (slave, own address `0x30`, `PB10`=`SCL`/`PB3`=`SDA`), with one external pull-up resistor per net to `3V3` — same "loopback proves the mechanism without a second physical device" idea as `SPI1`'s `MOSI`→`MISO` jumper.

- **Open-drain, wired-AND electrical model**: unlike every previous peripheral's push-pull pins, I2C's `GPIOx_OTYPER` must select open-drain — a pin can only pull its line low or release it, never actively drive high. External pull-up resistors are what let a released line float back up to `3V3`; without them the bus has no way to reach a valid idle-high state at all.
- **Three different flag-clearing conventions on one peripheral** — a new record for "don't assume, check": `SB` clears via read-`SR1`-then-write-`DR`, `ADDR` clears via read-`SR1`-then-read-`SR2`, `AF` clears via a direct `&= ~bit` write, same shape as `TIM2`'s `UIF`. All three coexist inside one driver.
- **`CR2`'s `FREQ` field is a plain integer MHz value** (`16` for a 16 MHz `PCLK1`), not an enumerated/binary selector like most other config fields touched so far — easy to instinctively reach for a hex "mode" value instead.
- **`CCR`/`TRISE` are computed, not looked up**: standard-mode 100kHz at 16 MHz gives `CCR=80` (from the standard-mode duty-cycle formula) and `TRISE=17` (`max_rise_time_ns / T_PCLK1_ns + 1` = `1000/62.5 + 1`). Both bugs caught pre-hardware: `CCR`'s `F/S` bit (15) was initially set backwards (selecting fast mode while the math assumed standard mode), and `TRISE`'s clear mask was `0x1F` (5 bits) instead of the field's real 6 bits (`0x3F`) — didn't bite immediately only because the chosen value happened to fit in 5 bits anyway.
- **`OAR1`'s bit 14 must always be written `1`** — a fixed hardware requirement with no functional meaning, easy to forget since nothing about the name suggests it. The real 7-bit address goes in `ADD[7:1]`, i.e. `address << 1` — same shifted-by-one shape as the address+R/W byte written to `DR` during a scan.
- **Peripheral clock gating bit, missed on a whole second port**: `RCC_AHB1ENR`'s `GPIOBEN` (bit 1) was never set at all — only `GPIOAEN` had been needed up to this point. Every `configure_gpio()` write touching `PB3`/`PB8`/`PB9`/`PB10` had been silently inert the entire time, regardless of how correct the physical wiring was. Identical bug class to the very first GPIO milestone's clock-gating lesson, just recurring on a port this project hadn't touched before.
- **Wrong alternate function on `PB3`, not caught by pattern-matching from `I2C1`**: `I2C1`'s pins and `I2C2`'s `SCL` (`PB10`) are all `AF4`, which made it easy to assume `I2C2`'s `SDA` on `PB3` was `AF4` too — it's actually `AF9`, confirmed against ST's own alternate-function table. Selecting an alternate function that isn't actually implemented for a given pin is documented as producing *undefined* pin behavior, not "does nothing" — in this case, consistent with the physical symptom: `SDA` never settling to a clean idle-high, so `I2C1` saw the bus as permanently busy and `START` never fired at all (`while(!SB)` hung forever, for every single scan attempt, before even the first address).
- **`CR1`'s `ACK` bit is gated by `PE`, not just sequenced after it**: RM0368 documents `ACK` as continuously cleared by hardware *while* `PE=0` — not just at the 1→0 transition. Writing `ACK` before `PE` (the "enable last" order used everywhere else in this project, e.g. `TIM2`'s `CEN`, `SPI1`'s `SPE`) gets silently zeroed back out; `PE` has to go high *first*, then `ACK`. The one bit in this whole project so far where "configure everything, enable last" is the wrong order.
- **Debugging discipline — status flags alone can't distinguish "never happened" from "peripheral not really alive"**: `I2C2_SR1` reading `0` on a failed match is ambiguous by itself — a fully dead/unclocked peripheral reads back `0` there too. Escalated to reading back the *configuration* registers actually written (`I2C2_CR1`, `I2C2_OAR1`) instead of the status register, which is what surfaced the `ACK`/`PE` ordering bug directly (`CR1` read back `1`, not the expected `1025`) — same "prove the layer underneath before trusting the symptom" discipline as the USART milestone's LED-as-oscilloscope story, applied to registers instead of an external terminal.

Verified on hardware: `I2C1`'s scanner sweeps `0x08`–`0x77` once per `TIM2` tick and correctly reports `48` (`0x30`) as the only acknowledging address, with `I2C2`'s own `CR1`/`OAR1` readback confirmed matching what was written (`1025`/`16480`) before the scan ever ran.

## I2C milestone 2: master write, master read, and write-then-repeated-START-read (verified working)

Extended the same `I2C1`↔`I2C2` loopback rig from address-only scanning to real data transfer, built in three explicit stages: a plain master write, a plain master read, then both combined with a repeated `START` — the standard "set a pointer, then read from it" shape used by real EEPROMs/sensors.

- **The data phase introduces per-byte flags, unlike the address phase's once-per-transaction `ADDR`/`AF`.** `TxE` (buffer empty, safe to load the *next* byte) and `BTF` (byte fully shifted *and* acknowledged, safe to `STOP`) are different guarantees despite living one bit apart in `SR1` — stopping on `TxE` alone risks a `STOP` mid-shift or pre-ack. `RxNE` (bit 6) is the receive-side equivalent, self-clearing on a `DR` read exactly like `USART2`/`SPI1`'s `RXNE` already did.
- **`ACK`'s meaning flips depending on transfer direction.** During a write, the master doesn't use its own `ACK` bit at all — the slave acknowledges the master. During a read, the master is the receiver, so its `ACK` bit now tells the *slave* whether to keep sending (`ACK`) or stop (`NACK`) — same bit, opposite semantic role depending on which way data is flowing.
- **Single-byte read has a documented, mandatory special sequence**: clear the master's `ACK` bit *after* confirming `ADDR` is set but *before* clearing `ADDR` itself, then request `STOP` right away — not after the byte arrives. Getting this backwards doesn't error, it just means the NACK/ACK decision for that byte is whatever `ACK` happened to already be, since the decision is locked in the moment the clock resumes. Caught directly by the project's own standing rule ("don't rely on register reset values") — `I2C1`'s `ACK` bit had never been touched anywhere and merely happened to reset to `0`, which coincidentally is the value a single-byte read wants; made explicit instead of left accidental.
- **Repeated `START` keeps the whole transaction atomic** — no `STOP` between the write and the read halves, so nothing else on the bus can interject and change what's being addressed in between. Practically: no need to wait on `BUSY`/bus-free before it, since the bus was never released to begin with.
- **`START`/`STOP` are deferred requests, not instantaneous actions** — confirmed directly against RM0368's own wording (`STOP` "generated after the current byte transfer"), not just inferred. Setting `STOP` before `I2C2_DR` was even loaded with the byte to send still worked correctly: `I2C2` was still holding `SCL` low (a `TxE` stretch, waiting for its own `DR` to be written), so hardware simply parked the `STOP` request until the byte transfer it's deferred against actually happened. Software's line-by-line ordering doesn't have to match the wire's electrical ordering — hardware's own state machine resolves that.
- **`NOSTRETCH` (`CR1` bit 7, default `0` = enabled) is the mechanism behind every stretch hit this whole build.** Slave-side `ADDR`, `RxNE`, and `TxE` can each independently hold `SCL` low until serviced — met all three across this milestone (address match, receiving the write's payload, and needing a byte loaded before sending the read's reply). A real interrupt-driven slave services these invisibly from its own ISR; here, with `I2C2` running no ISR of its own, the master's synchronous polling loop had to do all of that servicing by hand, on `I2C2`'s behalf, or the bus would stay parked indefinitely.
- **Real bugs caught building this, roughly in order**: a string-literal-into-`char` type error (`"A"` vs `'A'`) from reaching for double quotes out of habit; an early draft that reused the whole address-scan loop and wrote the *payload* byte into the address-phase `DR` write instead of as its own separate second write; `RxNE` checked on the wrong bit *and* the wrong polarity (read `TxE`'s bit, waited for it to clear instead of set); `BTF` checked against `TxE`'s bit number by the same copy-paste; a missing wait for the second (repeated-`START`) `ADDR` event entirely — code proceeded straight to clearing `ACK`/`ADDR` on the assumption the address had already been acknowledged, which happened to work only because the preceding polling loops had already burned enough real time for the event to resolve, not because it was actually synchronized; and the second `ADDR` clear reading only `SR1`, never the matching `SR2`, leaving the clear sequence incomplete. None of these produced compiler errors — every one only showed up as either a hang or silently wrong data on real hardware.

Verified on hardware: `I2C1` writes `'A'` to `I2C2` and `I2C2`'s own received byte reads back correctly (`65`); a standalone master read of a byte `I2C2` loads into its own `DR` returns correctly on `I2C1`'s side; and the combined write-then-repeated-`START`-then-read prints both `65` (write confirmed landed) and `69` (`'E'`, read confirmed correct) every cycle, steady and repeatable.

## PWM milestone: TIM4 channel 1 driving an external LED, static duty then a smooth breathing fade (verified working)

First peripheral built on a *second* timer running alongside `TIM2`'s existing 1Hz tick, specifically to avoid coupling PWM frequency to that tick. Landed on `TIM4_CH1` (`PB6`) after `PB9` (already `I2C1_SDA`) and `PB7` (real, but board-inaccessible without a Morpho-only cable) were both ruled out.

- **Duty cycle is a time ratio, not a voltage** — `duty = CCR/(ARR+1)`, the fraction of each counter period spent with `CNT` below the compare threshold. In PWM mode 1, output is active while `CNT < CCR`, inactive once `CNT` reaches it, until the counter wraps and the cycle repeats. This is also what makes PWM behave like a DAC substitute at all: fast enough switching averages into perceived brightness (or voltage, through a filter) purely from that ratio.
- **`CCMR1` and `CCER` are the two new register categories this milestone**, and they interact in the same two-layer shape as clock gating and `SPI1`'s `SSM`/`SSI`: `CCMR1` decides *how* a channel's comparator behaves (`OC1M`/`OC2M`'s 3-bit mode field — `110` selects PWM mode 1 — plus `OC1PE`/`OC2PE` preload enable), but `CCER`'s `CC1E`/`CC2E` decides whether that result ever reaches the physical pin at all. Both registers pack two channels into one 32-bit word split into two halves (`CCMR1`: channels 1/2 in low/high bytes; `CCER`: 4-bit blocks per channel) — channel 2's bits (`OC2M`=`[14:12]`, `OC2PE`=bit 11, `CC2E`=bit 4) and channel 1's (`OC1M`=`[6:4]`, `OC1PE`=bit 3, `CC1E`=bit 0) are the same layout, just shifted by one byte/nibble.
- **Frequency depends on `PSC` *and* `ARR` together, not `ARR` alone** — `freq = SourceClock / ((PSC+1)×(ARR+1))`. Copying `TIM2`'s exact `PSC`/`ARR` values first gave a 1Hz PWM (visibly blinking, not dimming — defeating the entire point of using a high enough frequency to be imperceptible). Later, growing `ARR` alone (for finer duty-cycle resolution) dropped frequency further, to `10Hz`, since nothing compensated on `PSC`'s side — resolution and frequency are two separate trade-offs against the same two registers, not one knob.
- **Board-level pin mapping bit twice, correctly resolved only by going to the primary source.** Two wrong pin claims in a row (`PB7`≠`D4`, actually `PB5`, and `PB7` isn't on the Arduino header at all — only the Morpho connector; then `PB6`≠`D8`, actually `PA9`) came from trusting secondary summaries instead of checking directly. The MCU datasheet's alternate-function table only answers "what can this silicon pin do" — which Arduino `D#` label a specific Nucleo board's silkscreen assigns to it is a board-design decision documented only in the Nucleo-64 user manual (UM1724), not the chip datasheet. `PB6` is actually `D10`, confirmed directly from UM1724's own connector table, which even names `TIM4_CH1` next to it explicitly.
- **Diagnostic technique reused from the very first LED milestone**: when the LED didn't light at all, bypassed `AF`/PWM entirely and drove the pin as plain GPIO output first, to isolate "is the wiring/pin/LED physically correct" from "is the peripheral configuration correct" before assuming either. Confirmed the wiring only after the pin-mapping bug above was found and fixed.
- **A "smooth" transition needs pacing from outside the loop, not a tight sweep inside one tick.** First attempt swept the full `0`→`99`→`0` range with two unpaced `while` loops inside a single `tick_flag` event — completing in microseconds, no different from the LED just sitting at `0%` the entire time, since nothing paces the individual steps. The fix: exactly one step per `tick_flag` event, with the current direction held in a variable that survives between calls (not re-derived each time), flipping at each boundary. The tick's real, physical spacing between calls is what makes the change visible — collapsing the whole ramp into one event throws that away entirely.
- **Shared trigger, coupled side effect**: speeding up `TIM2`'s tick (to pace the fade faster) also sped up `i2c1_scan_bus()`, since both are driven by the same `tick_flag`. Worth remembering whenever a single flag drives more than one independent behavior — tuning one consumer's timing silently retunes every other consumer sharing it.

Verified on hardware: static `50%` duty on `TIM4_CH1`/`PB6` produces a steady, visibly dimmed (not blinking) LED at `~100Hz`; sweeping `CCR1` one step per tick with direction reversal at each boundary produces a continuous, visibly smooth breathing fade.

## FreeRTOS milestone: interrupt-driven I2C1 scanner as a real task, running alongside a PWM task under the scheduler (verified working)

Converted the polling `i2c1_scan_bus()` state machine to fully interrupt-driven, moved it into a FreeRTOS task (`vI2CTask`) synchronized via task notifications, and ran it concurrently with `vPWMTimerTask` under the real scheduler — the first milestone combining an RTOS with a hand-rolled register-level driver in this project.

- **`I2C1_EV` and `I2C1_ER` are two separate, independent NVIC lines, not one** — this was the actual root-cause bug, not a red herring. `SB`/`ADDR`/`BTF`/`TxE`/`RxNE` interrupt via `EV` (`IRQ31`); `AF` and every other error condition interrupt via a completely separate `ER` line (`IRQ32`), confirmed directly against ST's own HAL example (`I2Cx_EV_IRQHandler` and `I2Cx_ER_IRQHandler` wired as two distinct handlers, not one). The first interrupt-driven attempt put the `AF` check inside `I2C1_EV_IRQHandler` — it compiled, linked, and even served `SB` correctly, but any non-ACKing address hung forever, because the NACK's actual interrupt request was going to a vector nobody had enabled or implemented. Confirmed via an ISR entry counter: exactly one `EV` entry (for `SB`), then permanent silence.
- **Both `EV` and `ER` need their own NVIC priority set once FreeRTOS is in the picture.** Any ISR calling a `...FromISR()` function must sit at/below `configMAX_SYSCALL_INTERRUPT_PRIORITY`, and that now applies to *both* lines, not just the one originally converted. `IRQ32` (`I2C1_ER`) lives in a different priority register than `IRQ31` (`I2C1_EV`) — `NVIC_IPRx` packs 4 IRQs per 32-bit register, so `IRQ31` is byte 3 of `IPR7` while `IRQ32` is byte 0 of the *next* register, `IPR8` — a new register macro, not reusable from the existing `IPR7` one.
- **`BUSY` can get genuinely stuck at 1 from an earlier interrupted transaction, independent of wiring.** RM0090's documented recovery is `SWRST` (`CR1` bit 15): set then clear, forcing `SDA`/`SCL` released and resetting the peripheral's internal state machine. Also caught: `BUSY`'s bus-monitoring logic isn't live until `PE` is set, so checking `BUSY` before `PE` risks a false "clear" reading that flips back to stuck the instant `PE` actually goes high — `PE` has to come first, then check `BUSY`.
- **The most valuable single debugging move was reverting to a known-good control, not adding more instrumentation.** After ruling out several hypotheses (weak pull-up, RC timing, wiring) without resolving the hang, rebuilding the *exact* historically-verified polling version — no FreeRTOS, no interrupts, no CMake, same register sequence that was already logged as working — and confirming it still worked identically proved the bus/wiring was never the problem, and re-scoped the entire remaining investigation to the interrupt-conversion layer alone. Chasing register-level theories further before doing this would have kept implicating hardware that was never at fault.
- **A secondary, timing-sensitive stall was never fully root-caused, and that's recorded honestly rather than papered over.** Back-to-back transactions in the interrupt-driven sweep occasionally stalled a few cycles in (`SR1`/`SR2` both quiet, no error flag, software state never reaching `DONE`) — reproducible 10/10 times under one exact build, then gone under a build with a few more instructions added (an entry-count diagnostic), and never recurred despite deliberately trying to reproduce it again with a purpose-built trace buffer logging the last 8 interrupt entries. The leading theory — a new `START` racing the previous transaction's not-yet-complete `STOP` — doesn't fully hold up against the actual timescales involved (CPU-instruction-count differences are nanoseconds; a real `STOP` condition takes microseconds), so it's logged as unresolved and latent, not fixed, in case it resurfaces later.
- **Diagnostic escalation ladder used throughout, in order of how much a single symptom could distinguish**: single-letter UART breadcrumbs to prove an ISR is entered at all (independent of its own logic) → bounded busy-waits with a spin counter instead of unbounded hangs, so a failure still reports *something* → full raw register dumps (`SR1`/`SR2`, both master and slave) at the point of failure instead of guessing bit-by-bit → a small ring-buffer trace log of the last N interrupt entries (handler, state, `SR1` at entry) once a single final snapshot couldn't distinguish between competing hypotheses. Each step was reached only once the previous one stopped being decisive.
- **`i2c_last_ok` (success vs. `AF`-aborted) has to gate what a consuming task prints.** Both the success path (`I2C1_EV`'s `READ_AVAILABLE` case) and the failure path (`I2C1_ER`'s `AF` case) wake the same blocked task via the same notification, so without this flag `vI2CTask` would print stale/meaningless `i2c_sended_data`/`i2c_received_data` for every non-ACKing address in the sweep, not just the one real device.

Verified on hardware: `vI2CTask` sweeps `0x08`–`0x77` under the real FreeRTOS scheduler, entirely interrupt-driven (no polling loops in task code), correctly printing `65`/`69` (`'A'`/`'E'`) only for the genuinely ACKing address (`0x30`) and silently skipping every NACK; `vPWMTimerTask`'s breathing fade keeps running concurrently on the same core, confirming the scheduler is genuinely interleaving both tasks rather than one blocking the other.

## Analog thermistor milestone: NTC + LM393 comparator module, `A0` read via `ADC1`/`DMA2` on `PA1` (verified working)

Repointed the existing single-channel `ADC1`/`DMA2` pipeline (previously reading a now-unplugged potentiometer on `PA0`) at a thermistor+comparator module's analog output instead — same DMA mechanism, different physical channel and source. Took an unusually long hardware-debugging path to get here, worth recording honestly since most of it wasn't a code bug.

- **`adc1_read()` racing the DMA controller, the first real bug**: the print task called the old CPU-polling `adc1_read()` (manual `SWSTART`, poll `EOC`, read `DR`) even though `ADC1` was already running in continuous mode with `DMA`/`DDS` silently consuming every conversion. Both were contending for the same `DR`/`EOC`, so the polling loop mostly read stale or racy leftover values instead of tracking real conversions. Fixed by reading `dma_sample_buffer[0]` directly — a single-byte peek needs no `HTIF`/`TCIF` synchronization, since DMA is already doing the acquisition work (same reasoning as the earlier DMA milestone's single-byte-read note).
- **Nucleo header pin-name collision, the actual root cause of "sensor demonstrably changes voltage, printed value never moves"**: the module's own analog pin is silkscreened `A0` — a label that also happens to be the Nucleo Arduino header's name for `PA0`. The sensor's signal wire was seated in the board's `A0` header pin (`PA0`, floating ever since the old potentiometer was removed) instead of `A1` (`PA1`, what `ADC1_SQR3`'s channel select and the `PA1` analog-mode `GPIO` config actually pointed at). A floating `PA0` settled into a deceptively stable-looking ~62-65 count — indistinguishable at a glance from a real reading — and survived a full independent electrical validation of the sensor itself (multimeter confirming real voltage swing directly at the module's legs) because that validation never touched the actual code path at all.
- **`ADC1_SMPR2` (sample time) had never been defined or written**, defaulting every channel to the hardware reset minimum of 3 ADC clock cycles — fine for a low-impedance source, questionable for this module's unbuffered resistor-divider tap. Added the register and set channel 1 to 480 cycles as a real correctness improvement (generous headroom regardless of actual source impedance, free given the 2-second print rate) — it turned out not to be the actual root cause of this particular symptom, but a genuine gap worth closing on its own merits.
- **A breadboard power instability chased in parallel, resolved by a connection reseat, not fully root-caused**: mid-session, plugging the module in collapsed `VCC` toward 0.7V. Reproduced identically across two different breadboards with fresh wires (ruling out one bad board), and the module's own `VCC`/`GND` legs measured open-circuit in isolation (ruling out a genuine internal short). Resolved by reseating the power connections — most likely a marginal/high-resistance contact that only manifested once the module was actually drawing real current, since an ohmmeter's tiny test current wasn't enough to reveal it. Same lesson as the potentiometer's earlier flaky-wiper finding: connection quality is part of signal integrity, not just firmware, and it can look exactly like a code bug from the outside.

## EXTI milestone: flame sensor → FreeRTOS-task-driven buzzer alarm on `EXTI4` (verified working)

First peripheral in this project triggered by an external GPIO edge rather than a timer tick or a peripheral's own internal event. An LM393-comparator flame sensor's digital output (`PB4`, Arduino header `D5`) fires `EXTI` line 4, which wakes a real FreeRTOS task (`vFlameAlarmTask`) via task notification; the task drives a buzzer on `PA4` (Arduino header `A2`).

- **Three-layer permission model, one layer beyond every previous interrupt in this project**: `SYSCFG_EXTICRx` (port mux — which port's pin *N* feeds EXTI line *N*) → `EXTI_IMR`/`RTSR`/`FTSR`/`PR` (mask, edge-select, pending/write-1-to-clear) → NVIC (same `ISERx`/`IPRx` layer TIM2/USART2/I2C already went through). The reason for the extra layer: GPIO has 16 *pins per port* but EXTI only has 16 *lines total* (one per pin number, shared across every port) — only one port can own a given line at a time, and `SYSCFG_EXTICRx` is what decides which one. `EXTICR2` covers lines 4-7 (the only register of the four this project needs so far); line 4's field is bits `[3:0]`, selecting port via `0001`=B.
- **`EXTI_PR` clears write-1-to-clear**, same convention as `DMA2_LIFCR`, *not* `TIM2_SR`'s direct `&=~bit` — worth checking per-peripheral every time, this project has now hit both conventions on different peripherals more than once.
- **Two real register-config bugs caught in code review, before ever touching hardware**: (1) `SYSCFG_EXTICR2`'s clear mask used `~(0xF << 4)` (line 5's nibble) while the set used `<< 0` (line 4's nibble) — clearing the wrong field entirely, immediately adjacent-bug shape to the MODER off-by-one-field mistakes from earlier milestones, just on a register this project hadn't used before. (2) `NVIC_IPR2`'s clear/set used byte 1's mask with byte 3's shift; `EXTI4`'s real IRQ number is 10, so its byte is `10 mod 4 = 2` — fixed to `~(0xFFUL << 16) | (5UL << 20)`. Left unfixed, `EXTI4` would have stayed at its power-on-reset priority 0, able to preempt FreeRTOS's own kernel critical sections — a real corruption risk, not just "wrong behavior."
- **Vector table entry existed and pointed at a function that was never defined** — `[26] = EXTI4_IRQHandler` (slot `16 + IRQ10`) compiled fine but would have failed at *link* time with no handler body anywhere. Same "compiles ≠ links ≠ correct" lesson as the USART2 milestone's missing-source-file bug, just caught before it ever reached that stage.
- **FreeRTOS ISR→task hand-off, same notification shape as `vI2CTask`**: `EXTI4_IRQHandler` clears `EXTI_PR` (write-1-to-clear), then `vTaskNotifyGiveFromISR(xFlameTaskHandle, &xHigherPriorityTaskWoken)` + `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)` — the task blocks on `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` the rest of the time, zero CPU cost while idle, identical pattern to every other interrupt-driven task in this project.
- **Software debounce, in the task, not the ISR**: a comparator sitting near its trip point can chatter for microseconds before settling. `vFlameAlarmTask` re-samples `GPIOB_IDR` after a `20ms` `vTaskDelay` before trusting the edge was real — deferring the real check out of the ISR, same "keep ISRs short" discipline as every earlier interrupt milestone.
- **Sensor polarity was assumed wrong initially, corrected only by direct multimeter measurement on the sensor's own `DO` pin** — bypassing the MCU entirely, same diagnostic escalation used for the thermistor milestone's power issue. Original assumption: idle high, falling edge on detection (`EXTI_FTSR`). Measured reality: **idles low (~0V), drives to 3.3V on flame detection** — a rising edge, not falling. Fixed by switching `EXTI_FTSR` → `EXTI_RTSR`. The task's own hold-until-clear polarity check (`if/while ((GPIOB_IDR>>4)&1) == 0`, "still low means still detecting") was a holdover from the same wrong original assumption and was *not* automatically corrected by fixing the trigger register — a separate bug, caught only once the buzzer's on/off behavior was tested end-to-end, fixed to `== 1` ("still high means still detecting") to match the confirmed real polarity.
- **A pin reassignment silently broke the consumer that referenced it by name, not by macro** — the buzzer moved from `PB2` to `PA4` (`gpio.c`'s `MODER`/output config updated correctly), but `vFlameAlarmTask` in `app_tasks.c` still hardcoded `GPIOB_BSRR` bit 2, the *old* pin's set/reset register. The interrupt and task were both genuinely firing correctly the whole time (confirmed by the task's own UART `F!` print executing) — the bug was entirely in which physical pin got toggled, not in the interrupt/notification chain at all, which the initial symptom ("buzzer silent") made easy to misdiagnose as "the interrupt doesn't wake the task." Fixed by adding a `GPIOA_BSRR` register macro (`0x40020018`, same `+0x18` offset from port base as `GPIOB_BSRR`) and repointing both the on/off lines to `GPIOA_BSRR` bit 4.
- **Dead hardware, diagnosed with a known-good-control swap, independent of any firmware**: an early "buzzer stays silent" symptom traced not to code or wiring at all, but a genuinely dead buzzer PCB module — confirmed by powering its `+`/`−` legs directly (bypassing its signal pin entirely) and getting nothing, then swapping in a second, bare 2-terminal buzzer element on the exact same GPIO pin and getting sound immediately. Same "swap in something you can be certain about" technique used earlier for pin-identity questions on the Nucleo header.
- **`GPIOx_IDR` is read-only — a GDB assignment expression doesn't change hardware state.** While debugging live over OpenOCD/GDB, `p GPIOB_IDR |= (1<<4)` printed a plausible-looking result but only computed a client-side OR on the *last read value* — it never actually writes anything, since `IDR` has no write path in silicon at all. Reading it plainly (`p/x GPIOB_IDR`, no assignment) is the only valid way to observe real pin state this way.
- **Live register debugging over GDB/OpenOCD without reflashing**: `openocd -f board/st_nucleo_f4.cfg` + `arm-none-eabi-gdb -x debug.gdb build\blink.elf`, breakpointing at the exact `vTaskStartScheduler()` call line rather than manually replicating `main()`'s init sequence by hand from the debugger. Manually poking peripheral registers immediately after enabling their `RCC_*ENR` clock bit risked a clock-domain-crossing/settling-time race (`Cannot access memory` on a freshly-enabled `GPIOA`'s registers) — breaking after real firmware init has already run sidesteps that whole class of ordering bug entirely, at the cost of only being able to inspect state that init already reached, not state before it.
- **`GPIOx_BSRR`'s high 16 bits actively drive low, they don't float** — worth restating here since it's what makes "turn the buzzer off" work at all: these pins are push-pull (`OTYPER` left at reset default 0), so `BSRR`'s `BR[n]` (bit `16+n`) genuinely pulls the output low rather than releasing it to be pulled by something else, unlike an open-drain pin's "off" state.

Verified on hardware: waving a lit lighter near the sensor produces a real, sustained `EXTI4` interrupt (confirmed via repeated `F!` prints matching the physical waving, not a spurious repeat), the buzzer sounds on `PA4` for the duration the sensor reports flame present, and falls silent again as soon as the sensor's `DO` line returns to its idle-low state — interrupt → FreeRTOS task wake → debounce → correct-pin buzzer drive → correct-polarity release, all confirmed end-to-end on real hardware.

Verified on hardware: printed ADC counts follow a physically plausible real-time curve — resting around `38`, dropping to `~19` under sustained contact with a very hot spoon, recovering upward once contact ends — over USART2, confirming the full `A0` → `PA1` → `ADC1` → `DMA2` → `dma_sample_buffer` → print pipeline is genuinely reading the sensor rather than a coincidentally stable floating pin.
